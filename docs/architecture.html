Architecture

Agent Observatory

A small hub that listens to your coding agents on every laptop and shows them as a live office. Agents push events in. A browser pulls the current state, then stays connected for updates. The hub never calls a model and never answers an agent with anything but an empty 204.

The whole flow

Two senders, one hub, one website. Everything on the write path ends in a single SQLite transaction, and only a stored event is announced to open dashboards.

What happens to one event

Example: Claude Code is about to run the Edit tool. This is the exact order inside the hub.

  1. Hook fires on the laptop. Claude Code posts its full hook payload to /ingest/claude with Authorization: Bearer … and X-Device: work-laptop.
  2. Token and device checked. A wrong token gets 401 before the body is parsed. A bad device name gets 400. Both use constant-time comparison.
  3. Collector strips it down. normalizeClaudeEvent parses only an allow-list of fields, maps PreToolUse to tool_started, and builds a fixed-template summary like “Edit tool started”. The raw body is never referenced again.
  4. Duplicate check. A dedup key such as tool_started:toolu_123, scoped to the session, turns a retried delivery into a no-op.
  5. One transaction. Upsert device, provider, project and session. Create the agent if new, link a subagent to its parent, run the status resolver, update tasks, filter the file path, insert the event.
  6. Broadcast. If the event was stored, the hub sends one SSE message containing the event plus every agent and task it changed. Demo events only reach demo viewers.
  7. Always 204. The response has no body, so a hook can never add context or a decision to Claude Code.

What is kept and what is thrown away

The hub receives more than it keeps. Claude Code sends prompts, tool input and tool output in every hook payload. The collector reads a short allow-list and the stored event shape has no field that could hold the rest. One free-text field, text, holds the prompt or what a tool was asked to do. It is trimmed, has likely secrets masked, and is only filled when CAPTURE_DETAIL=true (the default). Set it to false to keep fixed summaries only.

Stored

  • Event type, tool name, tool and task ids
  • Outcome (success or failure) and a short detail code
  • Fixed template summary text
  • With CAPTURE_DETAIL on: prompt text, shell commands, search patterns, URLs and subagent tasks, trimmed and with secrets masked
  • Project folder path, session and agent ids
  • File path, only when inside the session’s project folder, saved relative to it
  • Model id (main agent only)

Dropped at the collector

  • Tool output
  • File contents and edit bodies
  • Prompt text and tool input, when CAPTURE_DETAIL is off
  • Last assistant message
  • Transcript paths and file contents
  • File paths outside the project or any path using ..
  • Anything else the sender adds

How status is decided

A pure function in status/resolver.ts maps each event to an agent status. Silence never changes a status. “Stale” is worked out in the browser from the last event time, shown next to the status when a live agent has been quiet for more than 5 minutes.

How the data is shaped

Every id is built from its parents, so two laptops that reuse a session id, or open the same folder, never collide.

session id = provider ~ device ~ providerSessionId agent id = session id ~ (subagent id | "main") project id = hash(device + "\n" + folder path) demo device = "demo~" + name (demo data never mixes with real agents)

How the dashboard stays current

Two credentials, two doors

WhoCredentialOpensNever opens
Agent on a laptopINGEST_TOKEN as a bearer token/ingest/claude, /ingest/opencodeAny read route
You in a browserVIEWER_PASSWORD, then a signed 30-day cookie (HttpOnly, SameSite=Lax)Dashboard pages and /api/* reads and streamIngest

The cookie is expiry.HMAC, so the website and the hub verify it with no shared store. Login is limited to 5 failures per 15 minutes per address. By default the hub binds to 127.0.0.1. For several devices, set BIND_ADDRESS to a Tailscale or home Wi-Fi address, never 0.0.0.0.

What breaks and what happens

SituationResult
Hub process stopped, machine onConnection refused at once. Claude Code logs a non-blocking error and carries on.
Hub machine off or unreachableEach hook waits up to 2 seconds, so tools can feel slower. Events sent meanwhile are lost by design.
Same event delivered twiceDedup key makes the second one a no-op.
Subagent stop with no startIgnored (Claude Code fires these for internal helpers).
Dashboard loses its connectionShows “Reconnecting…”, reopens the stream from its last id, and the hub replays what it missed.
Agent goes quiet while workingStatus stays as it was. A stale badge appears after 5 minutes.
Bad payload400 with no body. The payload is never logged because it may hold prompts.

To add a third provider (for example another coding agent), write one collector that returns a NormalizedAgentEvent, register one route with collect('name', normalize), and add a display name. Storage, status, streaming and the UI need no change.
